## Decision: retain the current generator

ai-rulez `4.24.2` successfully generates and verifies Claude/Codex plugin artifacts. Native Claude validation passes for both manifests and marketplace; Codex reads all seven skills when supplied with a custom catalog. Frontmatter, skill bodies, and `agents/openai.yaml` contents survive generation, despite warnings saying that `agents/` subdirectories will be excluded. Both canonical sources and `plugin.content_root` pass resource-link validation and build seven standalone skills using our existing builder.

The following measured gaps prevent replacement of our packaging tooling:

These are gaps against this repository's packaging requirements, not a list of confirmed upstream bugs. Verification of listed provenance outputs is ai-rulez's documented scope; rejecting unlisted files would be an additional check. Plugin generation explicitly omits ordinary generation's stale-file cleanup; the reproduced deletion case is reported upstream as [a request for safe pruning](https://github.com/Goldziher/ai-rulez/issues/231). OpenCode generation deliberately owns its generated `package.json`, so preserving an existing Pi package requires separate output staging or additional integration.

| Contract | Result |
| --- | --- |
| Detect changed generated Markdown without repair | Pass: verification exits 1 and leaves the tree unchanged. |
| Reject an extra file under a generated skill | Fail: verification exits 0 for injected `obsolete.txt`. |
| Remove a skill after its canonical source is deleted | Fail: regeneration leaves its generated `SKILL.md` discoverable. |
| Generate our single-plugin Codex marketplace | Not generated; a custom catalog remains necessary. |
| Preserve Pi metadata when OpenCode generation is enabled | Fail: generated `package.json` replaces the Pi declaration and original package fields. |
| Regenerate after a derived source-version bump | Pass: verification detects stale output, regeneration succeeds, and both manifests become `0.1.1`. |

Shared root resources were supplied by the evaluation, not generated by ai-rulez. Standalone link rewriting and resource copying still require our builder. Metadata was derived into temporary TOML from root `package.json`; a real migration would need to maintain that derivation rather than introduce another authored version source. Adding cleanup, catalog generation, Pi preservation, and resource bundling would keep most of our current responsibilities while adding a generation dependency. Retain `tools/sync_packaging.py` and the existing builders.

No ai-rulez dependency is added to production packaging or normal CI. The temporary [prototype configuration](prototype-config.toml) records the canonical case after its version-change experiment. Generated OpenCode output was inspected for package compatibility; it was not installed or validated against an OpenCode v2 runtime. This evaluation makes no new Pi, OpenCode, Hermes, or Antigravity support claim.

## Release configuration

The selected release-please action pins `v5.0.0` by commit and locks release-please `17.6.0`. Its actual Node strategy, constructed through its factory, produces:

| Scenario | Resulting version |
| --- | --- |
| First feature commit, no previous release | `0.1.0` |
| Fix after `0.1.0` | `0.1.1` |
| Feature after `0.1.0` | `0.2.0` |
| Breaking feature after `0.1.0` | `0.2.0` |

Every scenario includes a changelog update and preserves the Pi declaration, file allowlist, and other package fields. The remote releases API and tag listing were empty during bootstrap research. The release manifest starts empty and the explicit initial-version setting avoids assuming an already published release.

The release guard's four regression tests cover the exact merge, a later green commit after a failed merge, multiple pending merges across API pages, and nonqualifying PRs. Local `make check-all` passes all 40 tests and builds all four host bundles. The CI interpreter was exercised through uv's Python 3.12 selection, and actionlint `1.7.12` accepts both workflows.

These are local checks, native manifest reads, and offline release simulations. GitHub workflow execution, repository permission settings, branch protection, and first-release publication have not been exercised. See [CONTRIBUTING.md](../../../CONTRIBUTING.md) for enabling the workflow, obtaining a final-head check on a bot release PR, and recovering a pending release.
